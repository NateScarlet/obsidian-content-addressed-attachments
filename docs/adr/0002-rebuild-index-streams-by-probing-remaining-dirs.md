# 重建索引以「剩余目录探测」实现流式产出

重建索引（`CAS.objects()`）原先要把所有目录、所有分片下的每一个文件都 stat 成对象，并在内存里按 CID 聚合完毕才产出第一条记录。附件上万时，用户点下「重建索引」后长时间没有任何进度反馈，无法区分「正在工作」与「已卡死」；扫描期内存也随对象数线性增长。改为流式：按固定顺序（每个目录先正常区、后该目录的回收站）遍历，首次遇到某 CID 时，就地探测它在**尚未扫描的目录**中的副本（正常路径与回收站路径各一次 stat），补齐成一条完整记录后立即产出，并把该 CID 记入「已处理」集合；之后在其它目录再遇到同一 CID 直接跳过。

之所以必须补齐「剩余目录」，而不能「扫到哪个副本就产出哪个副本」，是因为重建索引扫描阶段的写入是对账式覆盖：仓库层 merge 只在 incoming 缺 `copies` 时沿用旧值。逐目录局部产出会让后扫到的目录覆盖先扫到的副本状态，并让已清理的回收站标记复活。代价是总 stat 次数由「每个副本实例 1 次」上升到「每个唯一 CID 最多 2×目录数 次」，换来首条产出只依赖前几个目录的列举，以及扫描期内存由 O(全部对象) 降到 O(已产出 CID)。

**Considered Options**:

- 逐目录局部产出，改由副本级对账时间戳 + 后续阶段按副本实例清理：总 stat 次数与现状持平、内存最省，但 `CAS.objects()` 的语义要从「每个 CID 恰好一条完整记录」变成「每个副本实例一条」，且副本级时间戳需要真正接入落库路径（当前持久化层只映射 `dir` 与 `trashedAt`），改动面与语义代价更大，否决。
- 保持全量聚合、只把聚合结果分批 yield：首条产出仍需等待全部扫描完成，未解决目标问题，否决。
- 回收时刻取 `min(既有 trashedAt, 磁盘 mtime)`：`rename` 不改 mtime 且 CAS 内容不可变，磁盘 mtime 恒早于该副本进入回收站的时刻，`min` 永远选中 mtime，会把应用内记录的精确回收时刻覆盖成内容修改时间，否决。改为「已有记录优先，缺失才用 mtime」。

**Consequences**:

- 跳过规则依赖遍历顺序固定为「dir 的正常区 → 同 dir 的回收站 → 下一个 dir」：在正常区首见需探测当前 dir 起，在回收站首见可自下一个 dir 起（同 dir 的正常区已扫完且此前未标记该 CID，故不必回查）。若将来改变遍历顺序，跳过规则必须同步重推。
- 回收站副本的 `trashedAt` 以元数据既有值为准这条规则落在仓库层 merge（所有写入的必经点），而非各个调用方，因此 `save`/`index`/`trash`/`load`/`restoreIfTrashed`/重建扫描自动继承同一语义。
- `CAS.objects()` 与 `CAS.lookup(cid)` 的公开契约不变（前者仍是每个 CID 一条完整记录，后者仍是该 CID 在所有目录的全部副本）；「允许传入目录子集」的探测入口是私有实现细节，不引入「槽位」这一新概念。
- 扫描期内存仅保留已处理 CID 的集合（以 CID 字符串为键），不再驻留全部对象。
