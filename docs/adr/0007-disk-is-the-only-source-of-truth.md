# 磁盘文件系统是附件事实的唯一权威

插件维护一份 IndexedDB 附件元数据（副本所在目录、回收状态、按目录占用字节）。它看起来很
像权威数据源——文件管理器的「哪个附件在回收站」「下载目录占了多少」都从它读——但它随时
可能与磁盘不符：用户在系统文件管理器里删了附件、把 `.trash` 目录整个清空、把副本挪到别的
目录，插件都不会立刻知道；Obsidian vault 也没有可依赖的文件监听。

因此我们决定：**磁盘是唯一权威，元数据是可推导、可删除重建的索引。** 事实判定一律基于磁盘
探测（`adapter.stat` / `exists` 加上按 CID 推导路径），不依赖也不等待 IndexedDB；元数据
删除后按磁盘实际内容重建即可回到正确状态。两种丢失的严重级别不同——元数据整体丢失只是
需要重建索引，磁盘上真的没有文件才是真缺失。

由此推出一条正交约束：元数据写入只是索引维护，**不得阻塞任何只需要磁盘结果的操作**。典型
如 `resolveURL` 解析出落盘路径即可返回，不该被 IndexedDB 忙碌时的元数据写入拖住。

**Considered Options**:

- 让元数据成为权威，靠插件内的写入路径维护：读路径最快，但外部改动磁盘后索引会长期撒谎，
  而插件没有可依赖的监听来发现这类改动，否决。
- 元数据权威 + 每次读取顺带校验磁盘：等于每次读都做一次对账，索引不再省下任何 IO，否决。
- 元数据权威 + 周期性全量对账兜底：插件不常驻运行，对账窗口可能无限长；且对账与正常读
  路径要维护两套状态来源，否决。

**Consequences**:

- 元数据同步（`meta.get/merge/delete`）在写侧成批缓冲，无积压时零等待（见
  [ADR-0003](./0003-internal-buffer-merge-replaces-merge-batch.md)）；这条异步性对读路径
  不可见，因为读路径本来就不看索引。
- 只改磁盘、不更新元数据的操作必须自我收敛：清理删除副本后只发布失效信号，由后台索引按
  磁盘真相对账；唯一副本被删净的 CID 其记录一律删除，不再按引用状态保留（见
  [ADR-0006](./0006-cleanup-walks-download-dir-instead-of-metadata.md)）。
- 重建索引是这条原则的集中体现：以磁盘为准分两阶段清理残留，内存只保留已产出 CID 的集合
  （见 [ADR-0002](./0002-rebuild-index-streams-by-probing-remaining-dirs.md)）。
