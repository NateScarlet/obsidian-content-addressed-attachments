# 下载目录清理改为直接遍历目录，索引对账交给后台

下载目录清理原先从元数据枚举候选：`CASMetadata.find` 按 `hasCopyInDirs` 全表扫描（M 行）筛出每个候选后，再逐个走 `cas.lookup` 做跨目录磁盘探测（每个候选 O(2D) 次 stat，读创建时间），删除阶段由 `deleteCopyInDir` 再做一次 `collectCopies` 全量探测。全程串行，万级笔记、几十 GB 附件的 vault 里一次清理要几分钟，用户因此回避这个功能；配额自动清理更糟，它卡在每次新副本落盘的路径上。

改为直接遍历目标目录：新增 CAS 原语 `walkDirCopies(dir)` 产出目录内每个正常副本的 `{cid, path, stat}`，解析与重建索引共用同一套分片扫描逻辑（`scanShardCopies` / `copyFromPath`）。清理因此只做「每个分片目录一次 list、每个文件一次 stat、每个被删文件一次 remove」，全部发生在目标目录内，元数据表的规模与之无关。stat 与删除各自以有界并发进行（ADR-0004 的 `DEFAULT_PARALLEL_LIMIT`）。

遍历只认 CAS 命名约定（`dir/XX/{cid}.data`），未知命名格式的文件与外部拷入的文件不被触碰——与旧路径只覆盖已收录 CID 的范围一致。

**遍历与删除都是随机顺序，不按创建时间排序。** 分片目录与分片内的文件都被打乱：清理只需遍历一次，顺序不携带信息；随机化可避免单个报错文件在多次清理中反复卡住同一批副本。代价：配额清理在随机顺序下释放量会略微超出目标（在飞的删除无法取消），超出的副本同样是超保留期的可删副本，无实际损害。

**随之而来的行为变更**：删除不再由 `deleteCopyInDir` 同步收敛元数据，`removeCopyInDir` 只发布失效信号，副本状态由 `CASMetadataSyncService` 按磁盘真相对账。因此**唯一副本被删净的 CID，其元数据记录一律删除，不再按引用状态保留**——旧实现会为仍被引用的 CID 保留一条 `copies: []` 的记录等待重新获取。理由与「磁盘为唯一可信源」一致：文件不在磁盘上了，索引就该反映这一点。笔记中的引用不受影响，重新获取会重建记录。ADR-0005 的「清理不因引用而豁免」不受影响，只是删除后的记录处置方式变了。

**Considered Options**:

- 保留删除时的引用判定（先探磁盘再按 `isReferenced` 决定记录去留）：需要把 `isCIDReferenced` 重新注入回 CAS 层，在一次磁盘 IO 的热路径上为每个副本追加一次引用查询，而结论只能影响元数据记录的有无——否定（违反「磁盘为唯一可信源」，且把策略塞回原语）。
- 用 `indexedAt` 代替文件修改时间判定保留期：`indexedAt` 是记录级时间而非副本级时间，同一 CID 的多个副本会共享它，语义不匹配，否定。
- 保留同步收敛元数据、只把枚举换成遍历：仍需为每个被删副本做一次 `collectCopies` 全目录探测，正是要消除的那部分开销，否定。
- 把 `mtime`/`size` 写入 `CASMetadataCopy` 从而免去 stat：需要数据库迁移，且 stat 只在保留期判定处必需，属独立优化，不在本次范围。
- 遍历顺序按创建时间排序（保留配额清理「删最旧」的原语义）：排序要求先把整个目录读进内存（万级副本的元数据数组），与「边遍历边删」的流式目标冲突；且 ADR-0005 已明确顺序不携带语义，否定。

**Consequences**:

- `CAS.deleteCopyInDir` 从接口移除（清理是它唯一的调用者）；随之失去最后一个生产调用者的 `isCIDReferenced` 与 `CASMetadataObjectFilters.hasCopyInDirs`（含过滤器分支与测试）一并删除，不留只被自己测试覆盖的孤儿代码。
- 清理的释放量取自 stat：未被元数据收录的副本同样被清理并计入释放量。
- 清理进行中，文件管理器「下载」标签页的占用数字要等后台对账完成才刷新，不再是清理返回即刷新。
- **返回值是实际删除量的下界**：`orderedParallelMap` 早停会关闭在飞投影而不等待它们（ADR-0004），因此达标即停时最多还有 `limit` 个副本已被删除但结果未被交付。为此计数与进度回调一律在主循环里做——若写在投影里，返回后仍会变化，`cleaningDirs` 已解锁而进度回调还在往已隐藏的 Notice 上写。
- **单个删除失败会中止整轮清理**（原语是 fail-fast）。这与随机遍历顺序是一条设计：随机化存在的意义就是让下次清理卡在别处，元素级隔离会把这个前提架空。
- 目录里一个 CID 命名非法（外部用了不兼容的哈希函数）的文件会让整轮清理抛出中止——与重建索引中的既有行为一致，只是现在它也在清理的热路径上。
